# plumberfranklintn.com — Astro clone

A static Astro rebuild of the WordPress/Elementor site at
<https://plumberfranklintn.com> (Plumber Franklin TN). 22 pages, cloned from the
live site's own HTML and its compiled Elementor CSS, verified by measured
computed-style diffs against production at 1440 / 900 / 390 px — **66 page
comparisons, 0 differences**.

Built to the team's [migration playbook](../MIGRATION-PLAYBOOK.md). Stack: Astro 5
`output: 'static'`, Tailwind v4 for our own components only, no UI framework, and
one serverless function: the contact form's action.

---

## Quick start

```bash
npm install
npm run dev                     # http://localhost:4321 — the only mode that runs the form

npm run build                   # → .vercel/output/static/
PORT=4331 npm run serve         # serves the build, honouring vercel.json's rules
```

Verification (build and serve first):

```bash
npm run compare                 # computed-style diff vs production at 3 widths
npm run functional              # 89 behavioural checks
npm run form                    # 21 checks over the action pipeline
npm run audit                   # every internal href/src/url() resolves
npm run sweep                   # content-quality report (feeds the bug register below)
```

Re-crawling the source site:

```bash
npm run crawl                   # → _extract/html/      (FORCE=1 to refetch)
npm run css                     # → public/wp/css/      every stylesheet handle
npm run fonts                   # → public/wp/fonts/    self-hosted Ledger, Lato
npm run extract                 # → src/fragments/, src/data/pages.json
npm run media                   # → public/wp-content/  images and the mirrored assets
npm run images                  # re-encode the uploads in place, same dimensions
npm run probe                   # → _extract/live-dom/  production's post-init DOM
```

> `npm run preview` is deliberately absent. It stops working once the Vercel
> adapter is installed (playbook §3.4); `npm run serve` replaces it and is closer
> to production anyway, because it applies `vercel.json`'s redirects and rewrites.

## How the clone works

The pages are **ported, not rebuilt**. `scripts/extract.mjs` splits each crawled
page into header / content / footer / popup fragments of Elementor's own rendered
markup, rewrites URLs to be root-relative, and records the page's metadata and its
ordered stylesheet list. One dynamic route (`src/pages/[...slug].astro`) renders 20
of the 22 pages from `src/data/pages.json`, re-linking Elementor's compiled per-post
CSS in exactly the order WordPress emitted it. That cascade is what makes the clone
pixel-accurate, so it ships verbatim rather than being re-derived. (`/404/` and
`/search/` have routes of their own — see below.)

What is *not* ported is the JavaScript. `src/scripts/elementor.js` replaces jQuery,
elementor-frontend, elementor-pro-frontend, smartmenus, PowerPack's frontend bundle,
Swiper, Elementor's dialog and lightbox libraries and the e-gallery plugin. It does
not reimplement their behaviour from scratch — it reproduces the **DOM contract**
each one created, read off the live site's post-init DOM with the probes in
`_extract/probe/`. That distinction matters: the compiled CSS lays out against
Swiper's generated classes and inline widths and against e-gallery's custom
properties, so the markup is the thing that has to match, not the animation.

Several widgets turned out to be built or moved in the browser. Each is reproduced
here to match the live DOM node for node:

| Widget | What the server sends | What the JS does |
| --- | --- | --- |
| PowerPack off-canvas menu | the panel inside the header widget | moves it to be `<body>`'s first child, then annotates the whole `<ul>` as a SmartMenus instance |
| Animated headline (highlight) | the heading, no marker | appends the double-underline SVG and drives `e-animated` / `e-hide-highlight` |
| Animated headline (rotate) | five phrases, none marked | cycles `…text-active` / `…text-inactive` and writes the wrapper's width |
| Elementor popup | the template, inline after the footer | **detaches it**, and re-inserts it into a dialog widget on open |
| Gallery | bare `<a>` items | writes `--columns` / `--rows` / `--aspect-ratio` on the container and `--column` / `--row` on each item |
| Portfolio grid | the article list | adds `elementor-has-item-ratio`, `elementor-active` and the per-thumbnail fit axis |
| Reviews carousel | three slides | Swiper's classes, loop clones, indexes and bullet row |
| Image lightbox | nothing | the whole dialog + Swiper slideshow, plus two stylesheets no page links |

### Layout

```
scripts/           crawl → css → fonts → extract → media pipeline, plus the
                   compare / functional / form / audit / sweep harnesses
src/fragments/     ported Elementor markup (regenerated by `npm run extract` —
                   never hand-edit; corrections go in src/lib/fixes.ts)
src/data/          pages.json: one record per cloned URL
src/layouts/       BaseLayout.astro — the <head> cascade and page shell
src/pages/         [...slug].astro, 404.astro, search.astro
src/scripts/       elementor.js — the DOM-contract runtime
                   form.js      — the Book Appointment form's client half
src/actions/       index.ts — the one serverless endpoint
src/lib/           pages.ts, fixes.ts, and the form backend (env, turnstile,
                   ratelimit, db, email)
db/schema.sql      run once in Neon
public/wp/         mirrored stylesheets and self-hosted fonts
public/wp-content/ mirrored uploads — 143 files, 52 MB
```

### The two pages that are not just fragments

**`/404/`** is the theme's own "page can't be found" template, captured from a URL
WordPress is guaranteed to miss. Astro emits it at `404.html`, which Vercel serves
for any unmatched path.

**`/search/`** is WordPress's search results page. WordPress answers `/?s=<term>`,
so losing that URL would be a regression (playbook §1); `vercel.json` rewrites the
query form onto this route, and the search widgets — on `/404/`, on the author
archive and on this page itself — keep the `action="/"` WordPress gave them. The
template was captured with a fixed probe term, and `src/pages/search.astro` puts the
real term back into the heading, the input and the document title. **It always finds
nothing — see bug 4.**

## The form

The site has one form: Gravity Forms form 1, "Book Appointment", rendered through
PowerPack's `pp-gravity-forms` widget. It sits inside Elementor popup 189, which
every page carries, and appears a second time inline in the body of `/contact-us/`.

Gravity Forms posts to WordPress, so it stops delivering the moment WordPress is
switched off. This is a BlendMode build (playbook §4c), so the form is rewired to
our own serverless action — **the markup is not.** Every class, id and label
survives untouched, because that markup *is* the design: `gforms_formsmain_css` and
`widget-pp-gravity-forms` style the `gform_wrapper` class tree, and a hand-rolled
replacement would look nothing like the rest of the page. `scripts/extract.mjs`
swaps only the plumbing (`rewireForm`), and `src/scripts/form.js` drives the same
markup, writing its error and success states in Gravity Forms' own classes.

The pipeline in `src/actions/index.ts`, in order:

1. **Zod validation** — field for field as Gravity Forms had it: Email, Phone and
   both selects required, Name and Message optional. The select values are pinned
   to the options the markup offers, so a hand-built POST cannot write arbitrary
   text into the client's inbox.
2. **Honeypot** — Gravity Forms' own hidden field, kept and renamed. Checked first,
   so a bot never costs a Turnstile call; it is shown the same success a person is.
3. **Rate limit** — 3/min/IP, in memory. Advisory on serverless and documented as
   such in `src/lib/ratelimit.ts`.
4. **Cloudflare Turnstile**, verified server-side, failing closed — including when
   the verifier is unreachable. Skipped with a loud log warning until
   `TURNSTILE_SECRET_KEY` is set, so the site can deploy before service setup.
5. **Neon**, first, as the source of truth. A failed write fails the request.
6. **Postmark**, second, in a `try`/`catch`. An email outage never loses a stored
   lead; the failure goes to the Vercel logs.

Two changes are visible to a visitor, and both are deliberate:

* **reCAPTCHA becomes Turnstile.** The widget is configured `interaction-only`, so
  it renders nothing unless Cloudflare actually wants a challenge — the same
  zero-height footprint the invisible reCAPTCHA badge had, which is why the form's
  geometry is unchanged from production.
* **Without JavaScript the form no longer does anything.** Gravity Forms degraded
  to a plain POST; an Astro action cannot. This is the same trade the reference
  implementation makes.

### What still needs doing before it delivers

Follow playbook §5 — Neon, Postmark, Turnstile, then the environment variables.
Everything is in `.env.example`. Two notes specific to this site:

* **The confirmation text is a guess.** Gravity Forms' confirmation lives in the
  WordPress admin, and it is not in any served page, so the clone uses the plugin's
  default: *"Thanks for contacting us! We will get in touch with you shortly."* If
  the client had customised it, paste the real text into `CONFIRMATION` in
  `src/actions/index.ts`.
* **`SITE_OWNER_EMAIL` is `support@blendmode.com`.** Gravity Forms' own
  notification address is admin data and could not be read from any served page,
  so leads go to BlendMode rather than being guessed at. Change it in the Vercel
  project (and redeploy) if the client wants them delivered somewhere else.

`npm run form` covers everything the playbook's §6 checklist can automate:
validation, the honeypot, the rate limit, the CAPTCHA (accepted, rejected,
replayed, unreachable, unconfigured) and store-before-email. It runs entirely
offline, against a local stub of Cloudflare's siteverify — driving the real service
made checks fail for reasons unrelated to the code, and worse, made the fail-closed
check pass because the connection was being reset rather than because anything had
been rejected. The one case left is the happy path with a real widget token: a
human submits once against the deployment and confirms the row in Neon and the mail
at `SITE_OWNER_EMAIL` (playbook §3.6).

## Environment variables

Every one is optional at build time and documented in `.env.example`. The site
builds and deploys with all of them missing — the form then stores nothing, sends
nothing, and logs a loud warning that CAPTCHA verification is being skipped.

| Variable | What it does |
| --- | --- |
| `DATABASE_URL` | injected by the Neon integration; do not set it by hand on Vercel |
| `POSTMARK_SERVER_TOKEN` | this client's Postmark Server token |
| `POSTMARK_FROM_EMAIL` | an address on a domain verified in Postmark |
| `SITE_OWNER_EMAIL` | where leads are delivered — `support@blendmode.com` |
| `TURNSTILE_SECRET_KEY` | Turnstile secret |
| `PUBLIC_TURNSTILE_SITE_KEY` | Turnstile site key — the only value that may reach the browser |
| `IP_HASH_SALT` | salts the one-way hash of the submitter's IP; the raw address is never stored |
| `STORE_FORM_DATA_TO_DB` | default `true` |
| `SEND_EMAIL_TO_SITE_OWNER` | default `true` |
| `SEND_EMAIL_TO_CUSTOMER` | default `false` — needs copy the client has approved |
| `PUBLIC_SITE_URL` | canonical origin, default `https://plumberfranklintn.com` |
| `PUBLIC_WEBFONTS` | `on` by default — link Elementor's self-hosted Ledger and Lato |
| `PUBLIC_APPLY_FIXES` | build with the corrections in `src/lib/fixes.ts` applied |
| `TURNSTILE_VERIFY_URL` | test-only seam; never set it in Vercel |

## Original-site bugs

Per the playbook, the clone **reproduces production faithfully, bugs included**, and
lists them here for the client to decide on. `PUBLIC_APPLY_FIXES=on` builds with the
corrections that need no new information; the rest need a decision.

### Content — these are the ones worth reading first

1. **`/our-team/` is entirely placeholder content, and it is live.** Four staff
   cards reading *"John Due — Lead Owner — Lorem Ipsum is simply dummy text of the
   printing and typesetting industry…"*, plus two Lorem ipsum paragraphs above
   them. Nothing on the site links to the page — it is in neither the menu nor the
   footer — but it is in WordPress's sitemap, so it is indexable and reachable by
   anyone who finds the URL. **Recommendation: write it or unpublish it.** The
   clone ships it as-is because deleting a client's page is not a developer's call.

2. **The testimonials section is hidden but still shipped, and it is also
   placeholder.** On `/` and `/about-us/` an "OUR HAPPY CUSTOMERS" section carries
   three reviews from *"John Doe @username"* with Lorem ipsum bodies and Elementor's
   grey placeholder avatar. The section is marked
   `elementor-hidden-desktop elementor-hidden-tablet elementor-hidden-phone`, so it
   is invisible at every width — but the markup, the Swiper carousel and the
   placeholder image all still download on every visit to those two pages. Either
   fill it in and unhide it, or delete it.

3. **The whole site has no meta descriptions and no social preview markup.** Not one
   of the 22 pages carries a `<meta name="description">`, and there is no Open Graph
   or Twitter block anywhere — WordPress runs no SEO plugin here, so core's
   canonical tag is the entire SEO head. Every link to this site shared on
   Facebook, LinkedIn, iMessage or Slack renders with no image and no summary.
   Writing 22 descriptions is a copywriting job; flagging it is not.

4. **Site search always returns nothing.** `/?s=leak` — a word on half the pages —
   answers *"It seems we can't find what you're looking for."* The archive template
   queries posts, and this site has no posts, only pages. Verified against
   production and cloned exactly. Fixing it means designing a results list the
   original never had, which is a decision, not a bug fix.

5. **The author archive is an empty page WordPress advertises.**
   `/author/relplumbin/` renders the archive template with the same
   "can't find what you're looking for" message, and `wp-sitemap-users-1.xml`
   points search engines at it. `PUBLIC_APPLY_FIXES=on` marks it `noindex`; the
   clone's own sitemap already leaves it out.

### Markup and styling

6. **The Book Appointment form is rendered twice on `/contact-us/`.** Once in the
   page body and once inside popup 189, so the whole `gform_wrapper_1` / `gform_1` /
   `input_1_*` id tree appears twice in the served HTML. Nothing renders wrong
   today, because Elementor detaches the popup template at init and `/contact-us/`
   has no button that opens it — but it is invalid markup that anything reading the
   source sees, and it becomes a real bug the moment somebody adds a Book
   Appointment button to that page. `PUBLIC_APPLY_FIXES=on` suffixes the inline
   copy's ids.

7. **Five pages carry the popup and cannot open it.** Popup 189 is printed on all 22
   pages, but only 16 have a "Book Appointment" button. `/about-us/`,
   `/contact-us/`, `/our-team/`, `/author/relplumbin/` and the 404 page download the
   template, its stylesheet and its form markup for nothing. Harmless, but it is
   weight on every one of those pages.

8. **The footer credit is nearly invisible.** `wp-custom-css` sets
   `.footer-alright-custom a { color: #cecece3b }` — light grey at 23% opacity on
   the dark footer. The "BLEND MODE" link is effectively unreadable and fails
   contrast requirements comfortably. The same rule targets
   `.footer-alright-custom p`, which matches nothing: the widget renders its text
   directly in the container, with no `<p>` at all. So the copyright line itself is
   fine and only the link is affected — probably not what was intended either way.

9. **Two service pages appear twice in the menu.** The Drains submenu repeats
   `/plumbing/sewer-repair/` and `/plumbing/sewer-replacement/` as "Sewer System
   Repair" and "Sewer System  Replacement" — the second with a double space in the
   label. Both already appear under Plumbing under their own names.

10. **A heading level is skipped on `/our-team/`.** The page goes from `h2`
    straight to `h4` on the staff cards. Cosmetic to a sighted visitor, awkward for
    anyone navigating by headings.

11. **Every page's logo is a link with no accessible name.** The header logo is an
    `<img alt="">` inside an `<a href="/">` with no other content, so a screen
    reader announces an unlabelled link as the first thing on every page. One `alt`
    attribute fixes it.

12. **Ledger is asked for at a weight it does not have.** Elementor kit 273 sets
    `--e-global-typography-primary-font-weight: 600`, and Google publishes Ledger in
    one weight only (400). Every heading on the site is therefore synthetically
    bolded by the browser. It is cloned faithfully — both sides render identically —
    but if the headings ever look slightly muddy, this is why.

### Weight

13. **128 images ship at more than 2.5× the width they render at.** The header logo
    is served at 800px into a 196px slot on every page; several service-page
    photographs are 1439px natural into 271px slots. The mirrored uploads are 52 MB.
    `npm run images` re-encodes them in place — same filenames, same pixel
    dimensions, so no markup changes and the fidelity diff is unaffected — but the
    real win would be regenerating the `srcset` candidates, which changes markup and
    so is left as a decision rather than done quietly.

### Not a bug, but worth knowing

14. **The Gravity Forms honeypot label is randomised per request.** WordPress picks
    a different visible label each time ("Name", "X/Twitter", "Comments"…) inside a
    container its own CSS hides. The clone pins it to one value, which is invisible
    either way and stops the same popup hashing to fourteen different fragments.

15. **The `gf_browser_*` class is a server-side User-Agent sniff.** Gravity Forms
    stamps `gf_browser_chrome` / `_gecko` / `_safari` onto the wrapper and adjusts
    the selects' padding per engine. A static page cannot vary with the request, so
    the class is baked in and `src/scripts/form.js` re-derives the visitor's real
    one in the browser.

16. **The footer's copyright year is dynamic on WordPress, so the clone keeps it
    dynamic.** Baking "2026" into a static page would turn a self-maintaining line
    into one that goes stale next January — a regression the migration introduces
    rather than a bug it inherits. `src/scripts/elementor.js` refreshes it, which
    changes nothing while the build is current.

## Verification

| Harness | What it proves | Result |
| --- | --- | --- |
| `npm run compare` | computed styles and bounding boxes vs production, per element, at 1440 / 900 / 390 px | 66 comparisons, **0 differences** |
| `npm run functional` | the DOM contracts and behaviours the diff cannot see | 89 checks, 0 failures |
| `npm run form` | the action pipeline end to end, offline | 21 checks, 0 failures |
| `npm run audit` | every internal href, src, srcset entry and CSS `url()` resolves in the build | 2370 references, 0 broken |
| `npm run sweep` | content quality — feeds the bug register above | reports only |

Four defects in this clone were found by measurement rather than by looking, and
are worth knowing about if you maintain a sibling site:

* Elementor **detaches** a popup template at init and only re-inserts it on open.
  Leaving it in the document put five elements on the page that production does not
  have.
* PowerPack's off-canvas menu runs SmartMenus **collapsed**, so hover opens nothing.
  The runtime opened sub-menus on hover until production was measured doing nothing
  with the pointer parked on a parent item for over a second.
* The rotating headline's wrapper must be measured by **layout width**, not
  `getBoundingClientRect`, which includes the flip animation's `rotateX`. Reading it
  mid-flight wrapped the hero onto an extra line at 390px.
* Swiper writes `cursor: grab; transition-duration: 0ms` even on a container it
  cannot size — visible only on the reviews widget, which lives in a hidden section.

And two in the harness itself: animated headlines have to be **frozen** (by
swapping in a detached copy) rather than merely reset, because both sides' timers
fire again between the pin and the probe; and a background colour with zero alpha
has to compare equal whatever its channels say, because LiteSpeed rewrites the theme
reset's `transparent` to `#fff0` and the search page is the one page a query string
keeps out of its cache.

## Deploying

Import the repo at vercel.com/new; the standard config deploys with zero settings.
Then work through playbook §5 (Neon → Postmark → Turnstile → environment variables
→ redeploy), run the §6 acceptance checklist with a human submission, and point the
domain at Vercel per §8. `astro.config.mjs`'s `site:` is already the production URL,
so the canonical tags are right from the first deploy.
